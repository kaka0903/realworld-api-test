### 最值得写报告的两条

**BUG-RW-002**

```json
请求：{"user":{"username":"","email":"t11@test.com","password":"12345678"}}
响应：201 {"user":{"username":"","email":"t11@test.com","token":"..."}}
```

创建一个**没有用户名**的用户。而且再注册一次空用户名会返回
`400 user with this username already exists`——**提示完全误导**，让人以为是重名。

**BUG-RW-003**

```json

```

**空密码账号可以直接注册，并且能登录**——这是安全问题，不只是体验问题。

## 四、三类系统性偏差（比单个 bug 更有价值）

### S-01：鉴权失败一律返回 403（15 条用例受影响）

```
无 token 访问  -> 403 {"errors":["authentication required"]}
坏 token 访问  -> 403 {"errors":["could not validate credentials"]}
规范要求       -> 401
```

**为什么重要**：401 = 没认证（该去登录），403 = 认证了但没权限（该提示无权限）。
**前端无法据此决定跳不跳登录页。**

### S-02：冲突/认证失败一律返回 400（5 条）

```
用户名重复 -> 400（规范 409）
邮箱重复   -> 400（规范 409）
密码错误   -> 400（规范 401）
用户不存在 -> 400（规范 401）
```

**400 是"请求格式有问题"，409 是"和已有数据冲突"。** 混用会让客户端无法区分"改格式"和"换用户名"。

### S-03：重复操作不幂等（4 条）

```
重复关注 -> 400 you follow this user already
重复收藏 -> 400 you are already marked this articles as favorite
取消未收藏 -> 400 article is not favorited
```

规范没有明确要求幂等，但**返回 400 会让"重试"逻辑失效**——客户端重试一次就报错。

## 五、两个用例自身的错误（都不是产品问题）

**① API-01-01 正常注册 tester01**

执行器的 `setup()` 提前创建了 `tester01`，这条用例再去注册同名——**必然 400**。
**这是用例与夹具抢数据。**

**② API-04-03 更新为已存在的邮箱**

用例里写的是 `{"email":"tester01@test.com"}`，而当前用户**本来就是** tester01@test.com。
**改成自己的邮箱不算冲突**，所以返回 200 是正确行为。

> **教训：预期不符时，先怀疑用例，再怀疑实现。**
> 这条用例如果直接判成缺陷，就是一次误报。

## 六、这轮执行暴露的四个方法论问题

### ① 用例共享固定数据 → 不可重复执行

`tester01`、`测试文章一` 这些写死的数据，被多条用例共用。
**重跑一次，注册类用例就全部失败。**

### ② 有副作用的用例会污染后续用例

`API-04-06 更新 username` 把 tester01 改名后，**token 里的用户名对不上了**，
后面 `API-13-01`（删文章）直接 403 `could not validate credentials`。

**已把有副作用的用例排到最后，但仍会破坏"最后一段"的用例。**

### ③ 只用状态码断言，测不出业务正确性

`API-04-03` 返回 200，到底改没改成功？**状态码看不出来，要查响应体。**

### ④ 待判断用例（6 条）没有结论

预期写「200 或 422」等于没有预期。执行完必须回头定死。
