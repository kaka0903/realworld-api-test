# BUG-RW-001：密码长度未校验，7 位即可注册

| 项 | 内容 |
|---|---|
| **缺陷编号** | BUG-RW-001 |
| **标题** | 注册接口未校验密码最小长度，7 位密码可注册成功 |
| **发现版本** | `nsidnev/fastapi-realworld-example-app` main 分支 |
| **严重程度** | 中 |
| **优先级** | P2 |
| **关联用例** | API-01-07（password 只有 7 位）|

**前置条件**：服务正常运行，无同名用户

**复现步骤**

1. 发送注册请求：

```bash
curl -X POST http://<host>:8000/api/users \
  -H "Content-Type: application/json" \
  -d '{"user":{"username":"tester07","email":"t07@test.com","password":"1234567"}}'
```

**预期结果**：HTTP 422，提示 password 长度不足（规范要求最少 8 位）

**实际结果**：HTTP 201，注册成功并返回 token

```json
{"user":{"username":"tester07","email":"t07@test.com","bio":"","image":null,"token":"eyJ..."}}
```

**影响**：弱密码可注册，降低账号安全性；前端若依赖后端校验，用户可绕过长度限制。

**建议**：在 User 模型的 password 字段上加 `min_length=8` 校验。

# BUG-RW-002：username 允许空字符串

| 项 | 内容 |
|---|---|
| **缺陷编号** | BUG-RW-002 |
| **标题** | 注册接口接受空字符串作为用户名，且后续错误提示误导 |
| **严重程度** | **高** |
| **优先级** | P1 |
| **关联用例** | API-01-11（username 为空字符串）|

**复现步骤**

1. 首次注册空用户名：

```bash
curl -X POST http://<host>:8000/api/users \
  -H "Content-Type: application/json" \
  -d '{"user":{"username":"","email":"t11@test.com","password":"12345678"}}'
```

**预期结果**：HTTP 422，提示 username 不能为空

**实际结果**：HTTP 201，创建了一个**没有用户名**的用户

```json
{"user":{"username":"","email":"t11@test.com","bio":"","image":null,"token":"eyJ..."}}
```

2. 再次注册空用户名：

**实际结果**：HTTP 400 `{"errors":["user with this username already exists"]}`

**影响**

- 系统里出现无标识用户，后续无法通过用户名查询、关注、@ 提及
- **错误提示完全误导**：用户以为是重名，实际是空值未校验，排查成本高
- 空用户名可能在列表页、个人主页渲染成空白

**建议**：username 加 `min_length=1` 且 `strip()` 后非空校验；错误信息区分「为空」和「已存在」。

# BUG-RW-003：password 允许空字符串且可登录

| 项 | 内容 |
|---|---|
| **缺陷编号** | BUG-RW-003 |
| **标题** | 注册接口接受空密码，且空密码可直接登录 |
| **严重程度** | **高** |
| **优先级** | **P0** |
| **关联用例** | API-01-12（password 为空字符串）|

**复现步骤**

1. 用空密码注册：

```bash
curl -X POST http://<host>:8000/api/users \
  -H "Content-Type: application/json" \
  -d '{"user":{"username":"tester12","email":"t12@test.com","password":""}}'
```

**预期结果**：HTTP 422，密码不能为空

**实际结果**：HTTP 201，注册成功返回 token

2. 用空密码登录：

```bash
curl -X POST http://<host>:8000/api/users/login \
  -H "Content-Type: application/json" \
  -d '{"user":{"email":"t12@test.com","password":""}}'
```

**预期结果**：HTTP 401

**实际结果**：HTTP 200，返回 token

**影响**：**这是安全问题，不只是体验问题**——任何知道邮箱的人都能登录无密码账号；批量注册空密码账号可用于刷接口、占用资源。

**建议**：password 增加非空 + 最小长度校验；建议同时排查「空密码账号是否已存在于生产数据中」。

# BUG-RW-004：文章 title 允许空字符串

| 项 | 内容 |
|---|---|
| **缺陷编号** | BUG-RW-004 |
| **严重程度** | 中 |
| **优先级** | P2 |
| **关联用例** | API-09-04（title 为空字符串）|

**复现步骤**

```bash
curl -X POST http://<host>:8000/api/articles \
  -H "Content-Type: application/json" \
  -H "Authorization: Token <TOKEN>" \
  -d '{"article":{"title":"","description":"d","body":"b","tagList":[]}}'
```

**预期**：422 ｜ **实际**：201，创建了一篇无标题文章（`slug` 由空标题生成）

**影响**：文章列表出现空白标题条目；`slug` 生成规则异常（全部空标题会生成相同 slug，导致后续 409/400）。

**建议**：title 非空校验，并对 slug 加唯一性回退策略（如追加短 id）。

# BUG-RW-005：更新文章时 title 允许置空

| 项 | 内容 |
|---|---|
| **缺陷编号** | BUG-RW-005 |
| **严重程度** | 中 |
| **优先级** | P2 |
| **关联用例** | API-12-05（title 更新为空串）|

**复现步骤**

```bash
curl -X PUT http://<host>:8000/api/articles/<SLUG> \
  -H "Content-Type: application/json" \
  -H "Authorization: Token <TOKEN>" \
  -d '{"article":{"title":""}}'
```

**预期**：422 ｜ **实际**：200，标题被清空

**影响**：编辑页保存后文章标题变空，列表页出现空白项；**创建时不校验、更新时也不校验**，说明校验逻辑缺失的位置是同一处。

**建议**：与 BUG-RW-004 一并修复，把校验放在 schema 层而非路由层。

# BUG-RW-007：评论 body 允许空字符串

| 项 | 内容 |
|---|---|
| **缺陷编号** | BUG-RW-007 |
| **严重程度** | 中 |
| **优先级** | P2 |
| **关联用例** | API-15-02（评论内容为空）|

**复现步骤**

```bash
curl -X POST http://<host>:8000/api/articles/<SLUG>/comments \
  -H "Content-Type: application/json" \
  -H "Authorization: Token <TOKEN>" \
  -d '{"comment":{"body":""}}'
```

**预期**：422 ｜ **实际**：201

```json
{"comment":{"id":3,"body":"","author":{"username":"tester01"}}}
```

**影响**：出现空评论，评论区渲染空白；可被用于刷评论数。

**建议**：comment.body 加 `min_length=1`。

# 附：三类系统性偏差（不是单个 bug，建议整体反馈）

## S-01 鉴权失败统一返回 403，规范要求 401（影响 15 条用例）

```
无 token 访问   -> 403 {"errors":["authentication required"]}
无效 token 访问 -> 403 {"errors":["could not validate credentials"]}
```

**为什么是问题**：401 = 未认证（客户端应跳登录页），403 = 已认证但无权限（应提示无权限）。
统一返回 403 后，**前端无法区分这两种状态**，只能靠猜。

**建议**：区分 `HTTPBearer(auto_error=True)` 的 401 与权限校验的 403。

## S-02 冲突/认证失败统一返回 400，规范要求 409 或 401（影响 5 条）

```
用户名重复 -> 400（规范 409）
邮箱重复   -> 400（规范 409）
密码错误   -> 400（规范 401）
用户不存在 -> 400（规范 401）
```

**为什么是问题**：400 是「请求格式错误」，409 是「与已有数据冲突」。
用户改名失败时无法判断是格式问题还是重名。

## S-03 重复操作不幂等，返回 400（影响 3 条）

```
重复关注     -> 400 you follow this user already
重复收藏     -> 400 you are already marked this articles as favorite
取消未收藏   -> 400 article is not favorited
```

**为什么是问题**：客户端重试机制遇到 400 会判定为永久失败，**网络抖动后的重试直接报错**。
建议返回 200（幂等）或 409（语义冲突）。

# 附：一个用例设计错误（非产品缺陷）

**API-04-03 更新为已存在的邮箱**

用例里请求体是 `{"user":{"email":"tester01@test.com"}}`，而**当前用户本来就是该邮箱**，
所以返回 200 是正确行为。

**修正**：这条用例应该用**另一个用户**的邮箱，才能验证唯一性校验。
